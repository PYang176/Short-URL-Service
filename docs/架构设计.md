# 短链接平台架构设计

## 1. 架构结论

系统采用模块化单体，同一个代码仓库提供两个运行角色：

```text
cmd/api       HTTP API、管理接口、公开跳转
cmd/worker    点击消费、域名验证、Webhook、批量任务
```

不拆分微服务。API 和 Worker 共享领域代码，但可以独立扩容、独立发布和独立监控。

## 3. 技术选型

| 组件 | 选择 | 原因 |
| --- | --- | --- |
| HTTP | Gin | 路由、中间件和参数绑定成熟，适合完整 API 服务 |
| 数据访问 | sqlx | 保留显式 SQL，便于索引、事务和聚合优化 |
| MySQL | MySQL 8 | 保存业务数据、点击明细和预聚合分析结果 |
| Redis | Redis 7 | 缓存、限流、访客 HLL 和点击事件缓冲 |
| 事件队列 | Redis Streams | 已有 Redis，单业务、单消费组，允许最终一致 |
| 对象存储 | MinIO | 保存二维码 Logo，兼容 S3 |
| 反向代理 | Caddy | 自定义域名 Host 路由和 On-Demand TLS |
| 前端 | Vue 3 + TypeScript + ECharts | 完整管理端和可交互分析报表 |
| 指标 | Prometheus | HTTP、缓存、Stream 和 Worker 监控 |
| 日志 | `log/slog` | 标准库结构化日志，减少依赖 |
| 测试 | Go test + testcontainers + k6 | 单元、真实依赖集成和压测 |

## 4. 业务模块

```text
internal
├── app          应用装配与生命周期
├── auth         注册、登录、Token、密码
├── workspace    用户工作空间
├── link         链接管理、跳转决策、缓存
├── domain       域名验证、Host 路由、TLS 状态
├── qrcode       二维码配置、渲染、导出
├── analytics    点击事件、查询、分享报表
├── folder       文件夹
├── tag          标签
├── apikey       API Key
├── webhook      Webhook 投递
├── bulk         CSV 批量任务
├── admin        管理治理
├── platform     配置、MySQL、Redis、对象存储
└── transport    HTTP 中间件与响应
```

模块内部采用：

```text
handler -> service -> repository
```

跨模块依赖通过小型接口和明确的应用服务完成，不允许 Handler 直接访问其他模块 Repository。

## 5. 链接跳转链路

```text
HTTP 请求
  -> 解析 Host，确定域名
  -> 路径提取短码
  -> Redis 读取链接缓存
      -> 命中：检查状态、时间、密码
      -> 未命中：singleflight 合并回源
          -> MySQL 查询
          -> 写入缓存
  -> 返回 301/302 或错误页面
  -> XADD 点击事件
```

缓存值包含：

```json
{
  "linkId": "...",
  "status": "active",
  "destination": "https://example.com",
  "redirectCode": 302,
  "startsAt": null,
  "expiresAt": null,
  "passwordRequired": false,
  "routeVersion": 1
}
```

缓存 Key：

```text
link:v1:{domain_id}:{slug}
```

缓存策略：

- 未找到使用短 TTL 空值缓存。
- 普通缓存 TTL 为 30 分钟加随机抖动。
- 如果链接将在更短时间内过期，TTL 不超过剩余时间。
- 更新和删除完成后删除缓存。
- Redis 错误时记录指标并回源 MySQL。
- 跳转不依赖点击事件是否成功写入。

## 6. 点击分析链路

```text
cmd/api
  -> XADD shorturl:clicks

cmd/worker
  -> XREADGROUP
  -> 解析 User-Agent、IP 地理信息和 Referer
  -> 批量写入 MySQL 点击明细
  -> UPSERT 每日与维度汇总表
  -> XACK
  -> 定时 XAUTOCLAIM 处理超时 Pending
```

事件字段不使用原始 IP。访客哈希：

```text
visitor_hash = HMAC-SHA256(daily_salt, ip + user_agent + workspace_id)
```

一致性语义：

- Stream 写入成功后至少一次消费。
- MySQL 使用事件 ID 唯一约束保证重复消费幂等。
- 重复消费不得重复计算唯一访客。
- 统计允许 10 秒最终一致。
- Stream 写入失败不回滚跳转。

## 7. 自定义域名

域名状态机：

```text
pending
  -> verifying
      -> verified
      -> failed

verified
  -> disabled
  -> deleted
```

验证接口：

```go
type Resolver interface {
    LookupTXT(ctx context.Context, name string) ([]string, error)
    LookupCNAME(ctx context.Context, host string) (string, error)
}
```

实现：

- `DNSResolver`：生产环境真实 DNS。
- `FakeResolver`：开发与自动化测试。
- `VerificationWorker`：定期领取待验证域名，不把 DNS 查询放在用户请求中。

HTTPS：

- 生产环境使用 Caddy On-Demand TLS。
- Caddy 在签发证书前调用内部授权接口。
- 授权接口只允许已验证并归属于当前工作空间的域名。
- 开发环境使用 Caddy 内部 CA 和本地 Host。

本地模拟方式：

```text
DOMAIN_VERIFY_MODE=mock
DEV_CUSTOM_DOMAIN=go.local.test
127.0.0.1 go.local.test
```

模拟验证接口在 `APP_ENV=production` 时不会注册。

## 8. 二维码

二维码编码稳定的短链 URL，而不是目标 URL：

```text
QR payload: https://go.local.test/promo
link destination: https://example.com/campaign
```

二维码配置与渲染分离：

- 数据库保存样式配置和短链引用。
- 服务端生成可导出的标准 PNG/SVG。
- 前端提供实时预览和样式编辑。
- Logo 保存到 MinIO。
- 下载请求不需要重新创建短链。

## 9. API Key 与 Webhook

API Key：

- 格式为 `sl_live_<random>`。
- 数据库保存前缀和完整哈希。
- 明文只在创建时返回一次。
- 认证时按前缀查候选，再使用常量时间比较。

Webhook：

- 使用数据库 outbox 表保存待投递任务。
- Worker 领取任务并发送 HTTP 请求。
- 使用 HMAC-SHA256 对时间戳和请求体签名。
- 失败按指数退避重试。
- 连续失败达到阈值后自动停用。

## 11. 生命周期

API：

- 启动时初始化配置、日志、MySQL、Redis、路由和指标。
- 收到 SIGINT/SIGTERM 后停止接收新请求。
- 在超时时间内完成在途请求。
- 关闭数据库连接。

Worker：

- 启动 Consumer Group 和周期任务。
- 退出时停止领取新任务。
- 当前批次提交或安全回到 Pending 后再退出。
