# 数据库查询与索引设计

## 1. 容量假设

本设计以以下项目验收规模为边界，不宣称适用于无限增长的公网 SaaS：

- 单 MySQL 8.4 实例。
- 10 万个链接。
- 1000 QPS 缓存命中跳转验收目标。
- 1000 万条点击明细。
- 分析查询目标 P95 小于 100ms。

以上是设计和压测门槛，不是当前实测结果。表迁移、演示数据和查询实现完成后，必须使用 `EXPLAIN ANALYZE` 和实际数据重新验证。

## 2. 设计原则

1. 事务数据与分析数据都使用 MySQL，不引入额外分析数据库。
2. 所有业务主键使用 26 位 ULID，字符集固定为 ASCII。
3. 短码、域名等参与唯一约束的字段明确设置大小写规则。
4. 高频查询使用左侧连续的复合索引。
5. 链接列表使用游标分页，避免大偏移量 `OFFSET`。
6. 点击明细只追加，趋势查询读取预聚合表。
7. 聚合使用绝对覆盖，不使用不可重试的累加更新。
8. 所有查询先带 `workspace_id`，再按链接、时间和其他维度过滤。

## 3. 关键查询与索引

### 3.1 跳转时按域名和短码查找

```sql
SELECT
    l.id,
    l.workspace_id,
    l.destination_url,
    l.status,
    l.redirect_code,
    l.password_hash,
    l.starts_at,
    l.expires_at,
    l.expired_url,
    l.max_clicks,
    l.human_clicks,
    l.routing_rules
FROM domains AS d
INNER JOIN links AS l
    ON l.domain_id = d.id
WHERE d.hostname = ?
  AND d.status = 3
  AND d.deleted_at IS NULL
  AND l.slug = ?
  AND l.deleted_at IS NULL
LIMIT 1;
```

索引：

- `domains.uk_domains_hostname(hostname)`
- `links.uk_links_domain_slug(domain_id, slug)`

预期执行方式：

- 域名通过唯一索引定位。
- 链接通过 `domain_id + slug` 唯一索引定位。
- 正常情况下两表访问类型应为 `const/eq_ref`，不应扫描 `links` 全表。

注意事项：

- `links.slug` 必须使用 `ascii_bin`，否则大小写短码会冲突。
- 缓存命中时该查询不会执行。
- Redis 不可用时才回源该查询，因此它是降级路径而不是常态热点。

### 3.2 用户链接列表游标分页

```sql
SELECT
    id,
    domain_id,
    folder_id,
    slug,
    destination_url,
    title,
    status,
    created_at
FROM links
WHERE workspace_id = ?
  AND deleted_at IS NULL
  AND (created_at, id) < (?, ?)
ORDER BY created_at DESC, id DESC
LIMIT ?;
```

索引：

```sql
KEY idx_links_workspace_active_created (
    workspace_id,
    deleted_at,
    created_at DESC,
    id DESC
);
```

原因：

- 前两列固定工作空间和未删除状态。
- 后两列直接支持倒序范围和稳定排序。
- 游标由上一页最后一条的 `created_at + id` 组成，避免深分页扫描前 N 行。
- 不使用 `SELECT *`，减少无用的宽字段读取。

### 3.3 链接趋势

```sql
SELECT
    bucket_start,
    human_clicks,
    bot_clicks,
    unique_visitors
FROM link_time_stats
WHERE workspace_id = ?
  AND link_id = ?
  AND bucket_seconds = ?
  AND bucket_start >= ?
  AND bucket_start < ?
ORDER BY bucket_start ASC;
```

索引：

- 主键 `(workspace_id, link_id, bucket_seconds, bucket_start)`。

查询选择：

- 24 小时和 7 天：`bucket_seconds = 3600`。
- 30 天及以上：`bucket_seconds = 86400`。
- `unique_visitors` 只在单个时间桶内有效，不能直接跨桶相加。

### 3.4 工作空间趋势

```sql
SELECT
    bucket_start,
    SUM(human_clicks) AS human_clicks,
    SUM(bot_clicks) AS bot_clicks
FROM workspace_time_stats
WHERE workspace_id = ?
  AND bucket_seconds = ?
  AND bucket_start >= ?
  AND bucket_start < ?
GROUP BY bucket_start
ORDER BY bucket_start ASC;
```

索引：

- 主键 `(workspace_id, bucket_seconds, bucket_start)`。

原因：

- 工作空间仪表盘直接读取预聚合结果，不聚合所有链接行。
- 主键顺序与过滤和排序条件完全一致。

### 3.5 国家、设备和来源排行

```sql
SELECT
    dimension_value,
    SUM(human_clicks) AS human_clicks
FROM workspace_dimension_daily_stats
WHERE workspace_id = ?
  AND stat_date >= ?
  AND stat_date < ?
  AND dimension_type = ?
GROUP BY dimension_value
ORDER BY human_clicks DESC, dimension_value ASC
LIMIT 20;
```

索引：

- 主键 `(workspace_id, stat_date, dimension_type, dimension_value)`。

原因：

- 工作空间和时间是第一层过滤。
- 维度类型决定本次统计的国家、设备或来源。
- `dimension_value` 用于分组。
- 结果只保留前 20 条，应用层不能先取全量再截断。
- 工作空间排行不扫描 `link_dimension_daily_stats`，避免一次查询读取所有链接的维度行。

### 3.6 短码存在性检查

创建自定义短码时使用存在性查询，不使用 `COUNT(*)`：

```sql
SELECT 1
FROM links
WHERE domain_id = ?
  AND slug = ?
LIMIT 1;
```

索引：

- `uk_links_domain_slug(domain_id, slug)`

数据库唯一索引仍然是最终并发兜底。应用层查询只用于提前返回冲突，不能替代唯一约束。

## 4. 点击汇总的幂等写入

### 4.1 原始事件写入

Worker 使用批量 `INSERT IGNORE` 写入 `click_events`：

```sql
INSERT IGNORE INTO click_events (
    event_id,
    workspace_id,
    link_id,
    qr_id,
    domain_id,
    slug,
    clicked_at,
    visitor_hash,
    country,
    region,
    city,
    device,
    os,
    browser,
    language,
    referrer,
    utm_source,
    utm_medium,
    utm_campaign,
    utm_term,
    utm_content,
    is_bot,
    route_variant
) VALUES
    (?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?);
```

`event_id` 是主键。重复消费不会新增点击明细。

### 4.2 汇总使用绝对重算

汇总不能使用如下逻辑：

```sql
-- 错误：事件重复消费时会重复增加点击量
ON DUPLICATE KEY UPDATE human_clicks = human_clicks + VALUES(human_clicks);
```

正确方式是针对受影响的时间桶重新执行集合聚合，并用结果覆盖原有统计：

```sql
INSERT INTO link_time_stats (
    workspace_id,
    link_id,
    bucket_seconds,
    bucket_start,
    human_clicks,
    bot_clicks,
    unique_visitors
)
SELECT
    workspace_id,
    link_id,
    3600,
    DATE_FORMAT(clicked_at, '%Y-%m-%d %H:00:00'),
    SUM(CASE WHEN is_bot = 0 THEN 1 ELSE 0 END),
    SUM(CASE WHEN is_bot = 1 THEN 1 ELSE 0 END),
    ? -- 由应用层从 Redis HyperLogLog 计算后传入
FROM click_events
WHERE workspace_id = ?
  AND link_id = ?
  AND clicked_at >= ?
  AND clicked_at < ?
GROUP BY
    workspace_id,
    link_id,
    DATE_FORMAT(clicked_at, '%Y-%m-%d %H:00:00')
ON DUPLICATE KEY UPDATE
    human_clicks = VALUES(human_clicks),
    bot_clicks = VALUES(bot_clicks),
    unique_visitors = VALUES(unique_visitors);
```

为什么可重试：

- 聚合输入是已经去重的 `click_events`。
- 每一次都重算当前桶的绝对数量。
- 同一范围执行多次，结果保持相同。
- 最近时间桶可以周期重算，延迟到达的事件能够被吸收。

### 4.3 为什么不逐条累加

- 逐条更新会产生大量小事务和行锁竞争。
- ACK 失败后重复消费会导致点击量重复增加。
- 无法安全重放失败批次。
- 多条事件同时更新同一链接统计时容易形成热点行。

## 5. 执行计划验证

### 5.1 本地验证环境

验证日期：2026-11-12。

环境：

- MySQL 8.4.13 Docker 容器。
- 10,000 个链接。
- 100,000 条点击事件。
- 30 天点击数据。
- 表执行 `ANALYZE TABLE` 后运行 `EXPLAIN ANALYZE`。

该结果只证明当前索引方向和查询结构合理，不代表生产容量。

表和演示数据完成后，使用 MySQL 8 的 `EXPLAIN ANALYZE` 验证以下查询：

```sql
EXPLAIN ANALYZE
SELECT
    l.id,
    l.destination_url
FROM domains AS d
INNER JOIN links AS l ON l.domain_id = d.id
WHERE d.hostname = 'go.local.test'
  AND d.status = 3
  AND d.deleted_at IS NULL
  AND l.slug = 'launch'
  AND l.deleted_at IS NULL
LIMIT 1;
```

```sql
EXPLAIN ANALYZE
SELECT
    id,
    slug,
    destination_url,
    title,
    status,
    created_at
FROM links
WHERE workspace_id = '01...'
  AND deleted_at IS NULL
ORDER BY created_at DESC, id DESC
LIMIT 50;
```

```sql
EXPLAIN ANALYZE
SELECT
    bucket_start,
    human_clicks,
    bot_clicks
FROM link_time_stats
WHERE workspace_id = '01...'
  AND link_id = '01...'
  AND bucket_seconds = 86400
  AND bucket_start >= '2026-10-01 00:00:00'
  AND bucket_start < '2026-11-01 00:00:00'
ORDER BY bucket_start;
```

验收项：

- 跳转查询的域名和短码步骤使用唯一索引。
- 链接列表不会对大工作空间做全表排序。
- 趋势和维度查询使用范围索引。
- `rows examined` 与返回结果量处于同一数量级。
- 大表查询不得出现无范围约束的全表扫描。
- 查询 P95 目标小于 100ms；最终数字必须来自真实测试。

### 5.2 本地实测结果

| 查询 | 实际扫描或返回 | 本地耗时 |
| --- | --- | --- |
| 域名 + 短码跳转查询 | 唯一索引定位，返回 1 行 | 小于 0.01ms |
| 链接列表游标分页 | 索引查找，返回 50 行 | 约 0.13ms |
| 单链接每日趋势 | 主键范围扫描，返回 5 行 | 约 0.02ms |
| 工作空间每日趋势 | 主键范围扫描，返回 31 行 | 约 0.02ms |
| 工作空间国家排行 | 范围扫描 124 行 | 约 0.12ms |

对照结果：

- 直接在工作空间全部链接的 `link_dimension_daily_stats` 上聚合时，查询扫描约 100,000 行，本地耗时约 44.6ms。
- 增加 `workspace_dimension_daily_stats` 后，查询只扫描 124 行，本地耗时约 0.12ms。
- 因此正式设计同时维护链接级和工作空间级汇总表。

## 6. MySQL 注意事项

- MySQL 不支持部分索引，因此使用 `deleted_at` 复合列或生成列表达有效记录约束。
- 唯一索引允许多个 `NULL`，所以默认域名和有效文件夹名称使用生成列。
- `LIKE '%keyword%'` 无法使用普通 B-Tree 索引。链接标题搜索在数据量增大后需要评估 `FULLTEXT`，当前不提前增加。
- `VALUES(col)` 在较新的 MySQL 中属于兼容写法；优先保持项目统一，升级时再评估行别名语法。
- InnoDB 会自动为外键列创建索引，但仍应显式设计复合索引以覆盖真实查询。
- `click_events` 不使用 MySQL 原生分区。当前验收容量通过时间索引和保留清理控制；达到亿级明细后再重新评估。
